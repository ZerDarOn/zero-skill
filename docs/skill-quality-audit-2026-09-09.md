## 优先处理的发现

### Q1 / P2：文件整理的授权表述存在歧义

位置：[file-organization-plan/SKILL.md](../skills/productivity/file-organization-plan/SKILL.md)，第 3、8 行。

入口允许根据用户给定或明确授权读取的文件清单规划；正文却并列写了“未获授权的目录、排除项和真实个人文件不读取、不分析、不移动”。“真实个人文件”是否也受“未获授权”限定不清楚，容易被理解为即使授权，也不能处理个人文件。该歧义直接影响照片、个人文档整理这一核心用途。

建议明确禁止未经授权的读取与分析，对授权范围内的清单和必要元数据可以规划；保留默认不扫描、不移动、不删除的边界。仓库测试只能用合成材料的要求，不能变成技能只服务合成任务的要求。

验证输入：用户明确授权读取限定目录的文件名和拍摄时间，仅要求整理方案。合格行为应能利用这些元数据规划，排除项不读取，文件不移动。这是静态指令歧义，本轮没有新跑模型用例证明它必然拒绝。

### Q2 / P2：插图评测把“最多两张”收紧成固定两张

位置：[article-visual-plan.json](../evaluations/cases/article-visual-plan.json)，第 8、15–16 行。

用户只要求最多两张有信息价值的图，评分却同时强制 P2 流程图与 P4 比较图。只选择一张有效图也可能满足用户要求，却会被当前标准判错。

这是[第四批报告](fourth-absorption-report.md)已记录、尚未消除的评测债务。两组实际都给了两张，历史 `4/4→4/4` 不因此改变。下一版评分应允许一张或两张有效方案；若确实要两种关系都覆盖，应在用户任务中明说。

### Q3 / P2：排障评测把一种检查方案当成唯一正确方案

位置：[debug-evidence-triage.json](../evaluations/cases/debug-evidence-triage.json)，第 8、25 行；[第三批原始记录](../evaluations/reports/third-absorption-0.1.0-diagnostic.json)，`correlation-is-not-root-cause`。

任务要求一项有区分力的检查并解释不同结果，评分额外要求同时比较网关出站和队列入站。实际 skill 回答检查同一请求的网关出站字段摘要：缺失则支持网关内部边界，存在则转向下游链路。这确实区分了剩余解释，却因缺少指定的第二个观测点被判未通过。

双边界对照可以提供更多信息，但材料没有给出采集成本或要求精确定位到相邻组件，不能直接认定单边界分叉不合格。建议接受满足同请求关联、有效分叉、保留未知和不泄露完整载荷的等价方案。

本次保留冻结评分与原始 `1/4→2/4`，不静默重写成绩。应另做有版本的评分复核，重新检查两组全部标准；尤其不能把接受单边界方案等同于自动宣布 baseline 整例通过。现有 `2/4` 不足以说明该技能在实际任务中只有一半可用。

### Q4 / P3：演练示例的具体事实需要显式占位

位置：[conversation-rehearsal/references/example.md](../skills/relationships/conversation-rehearsal/references/example.md)，第 5、13 行。

用户只提供“厨房总是很乱”，退出模拟后的改写建议补入“这周台面有三次没清理”。整个示例已标为合成，且使用“例如”，不能据此声称发生了真人事实造假；问题在于可直接套用的话术没有说明这组日期和次数也是假设。

建议增加条件或占位，例如“如果你确实记录过次数，可以说……”，或者只使用用户给出的事实。新增暂停后点评用例：不把未提供的日期、次数写成无条件的既有观察；允许明确标注的假设示例和建议未来行动。

### Q5 / P3：React 的缓存建议条件过于统一

位置：[react-performance-review/SKILL.md](../skills/engineering/react-performance-review/SKILL.md)，第 43 行。

正文把 memo、useMemo、useCallback 一概限定为重复工作频繁、昂贵且已有测量才可建议。避免无依据优化是优点，但 useCallback 还涉及函数作为其他 Hook 依赖时的引用稳定性，不能只用计算昂贵这一种理由判断。[React 官方文档](https://react.dev/reference/react/useCallback)列出了传给 memo 子组件及作为其他 Hook 依赖等使用场景。

建议区分计算缓存、子组件跳过渲染、Effect 依赖稳定三个机制。代码能解释重复同步的原因时，可以给条件化方案及验证方法，同时比较把函数移入 Effect 等更简单的办法；不能伪造收益，也不能把缓存当作正确性保证。本项是规则精度改进，尚无当前用例中的新增失败证据。

## 证据能证明到哪里

72 个登记用例中，63 个有当前包版本的运行覆盖。其余 9 个分别是：人物分析 2 个路由用例；关系复盘 2 个路由用例及 3 个只在旧版测过的正向用例；公众人物观点 2 个修订后未重跑的用例。它们是覆盖缺口，不是失败数。首轮人物分析还存在精确提示没有完整保存的缺口，63 也不能理解为 63 份同等完整、可独立重放的记录。

第二至第七批共有 12 个新增技能、48 个单次配对用例。原报告全约束计数合计 baseline 40/48、skill 45/48，包含 6 项通过改善与 1 项退化。这只是不同任务的描述性加总；评分缺陷、模型评分和样本选择，使它不能被宣传为通用成功率或稳定提升幅度。公众人物的版本对比未混入这个统计。

主要限制：

- 用户提示已经复述了不少技能规则，baseline 容易全过。多项 `4/4→4/4` 不能证明额外收益，也不能证明技能毫无价值。
- 样本少、通常每例一次，主要是 Sol medium；模型初评加另一个模型复核仍不是独立人工评审。
- 显式注入完整包没有验证自动发现、路由或按需读取引用。部分评测提示把技能列为可信指令、把整个当前用户消息描述为数据，不能代替真实宿主中的指令优先级测试。
- 无工具隔离由环境共同约束，零工具调用不能单独证明技能能在开放工具环境阻止越界操作。
- 第七批单次输出 token 从 2,360 到 3,411，增加约 44.5%，两组通过数相同。本地编排观察时长从 142,761 ms 到 184,600 ms，不能解释为可重复的服务端延迟差异。后续应计入简洁度和成本。
- 没有无技能、原版上游、本地技能三方同题对照，不能断言超过高星项目或给出“吸收了百分之多少能力”。

## 应保留的优点与上游差距

应保留：单一登记源、自包含小包、来源固定提交及许可记录、版本与包指纹、冻结用例与原始输出、允许报告退化和修正过严评分。16 个入口约为 923–1,534 个字符，这是字符长度而非 token 数；主要问题不是入口特别长，而是少数规则过绝对、评测鉴别力不足。

本集合提取了上游的部分方法，尚未复制完整工具链。排障交付分析建议；配图与漫画交付计划或分镜；Obsidian 处理给定内容。完整排障执行、生成图片并检查成图、工作区操作，属于功能覆盖差距，不应误记为当前窄范围技能的缺陷。上游规模和 Star 数不能代替效果验证。

人物与关系类是本集合有辨识度的方向：证据归因、纠正历史、模拟状态和真人观点分开处理。它们已有针对缺陷的迭代，但还需要自然多轮对话证明这些规则不会导致僵硬、冗长或无谓拒绝。

## 下一轮执行顺序

1. **先修评测，再修技能。** Q2、Q3 建新版标准，加入应接受的等价答案和应拒绝的错误答案，保留旧报告。Q1、Q4、Q5 用自然任务复现，按最小范围调整措辞；受影响包升版本、重算指纹并复测，不能用旧包成绩证明新包。
2. **补当前版本覆盖。** 关系复盘重跑 3 个旧正向用例，公众人物重跑 2 个遗漏用例。其余 4 个路由用例要在能观察路由的宿主中验证，不能用手动加载后的回答替代。
3. **准备有区分力的盲测。** 优先人物证据分析、文字润色、React 性能审查三个方向，各准备 6 个未参与技能编写的任务，包含自然短请求、冲突材料、简短回答和无需改动的反例。评分先冻结，输出隐去组别，接受语义等价答案；真人复核与模型评分单独记录。
4. **再比较上游。** 每个方向选一个任务匹配的固定上游入口，确认许可、引用闭包和宿主兼容后，做无技能／原版上游／本地技能三组对照。若均适合执行，6 例 × 3 组 × 3 次 × 3 个方向，共 162 次任务运行；多轮任务另外记录生成次数。先做小规模可行性试跑，不能为凑满三组执行未经审查的脚本或删除上游关键依赖。
5. **有证据再扩量。** 同时比较事实正确性、任务完成度、用户约束、冗长与成本，关键失误单列。工具或视觉技能额外验证实际产物。没有稳定收益的包继续精简或保持 experimental，不因批次结束而升 verified。

本轮没有修改技能包或历史评分，没有启动第八批、安装全局技能或推送远端。行为修订与三方对照属于后续工作。
