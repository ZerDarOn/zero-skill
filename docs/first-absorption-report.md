## 用例驱动的设计目标

以下是写技能前从 planned 用例识别出的潜在基线风险，不是模型实测结果：

- 单字回复容易被扩写成确定动机或人格结论。
- 用户已有判断时，回答可能迎合主张并忽略材料中的直接反证。
- 被分析文本中的命令可能与真正授权混淆。
- 纠正发言人后，旧结论可能被静默覆盖或继续混用。
- “下一句怎么回”可能被长篇理论和阶段报告埋住。
- 发言人未知时，回答可能凭内容分配身份。
- 明确拒绝可能被错误重解释为试探，导致继续推进。
- 相邻的角色扮演、数据库关系、纯表达分析与回复建议需要在 description 和负向路由用例中分开。

在原有 11 个 planned 用例基础上，新增 `reply-advice-neighbor`，补齐人物分析不应抢占关系回复建议的反向边界；最终共有 12 个 active 合成用例。

## 人工审阅

- 两个入口只含 `name` 与单行 JSON 双引号 `description`，路径和名称与登记一致。
- 每个包可独立复制；没有本机绝对路径、兄弟技能或外部工具依赖。
- 两个示例均为合成材料，展示了片段定位、事实与解释分离、未知项和可执行表达。
- 人物技能保留反证与修订历史；关系技能将回复放在依据之前，并对明确拒绝设置停止推进边界。
- 输入材料中的命令只作为数据处理，不产生外部操作权限。

## 行为评测状态

本轮没有运行 12 组“无技能基线 / 加载技能”独立对照：当前编写会话已经读取技能与评分标准，不能充当隔离执行会话；同时也没有建立能验证 `expected_route: null` 的自动发现环境。因此没有生成 `evaluations/reports/` 证据文件，也没有把任何示例冒充真实输出。

后续要提升为 `verified`，仍需：

1. 在固定宿主和模型配置下运行全部 active 用例的基线与技能版本。
2. 对 `expected_route: null` 的用例使用真实自动发现环境，而不是显式调用技能。
3. 保存原始输出、耗时、人工理由、包与用例指纹；每项通过后再登记 evidence。
