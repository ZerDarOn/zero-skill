## A：React 性能审查

必要能力：

- 先依据材料识别 React 版本、客户端或服务端边界、是否使用框架及 Compiler、已测交互和用户范围。缺少某项信息但不影响局部结论时不阻塞，涉及该条件的建议写成条件判断。不要默认项目是 Next.js 或已启用 Compiler。
- 发现须连接代码位置或给定测量记录、额外工作发生的机制、实际适用条件和最小改善方向。实测瓶颈优先于风格偏好，静态猜测不能伪装成已测耗时或固定百分比收益。
- 并行仅针对独立且允许同时发生的操作；数据依赖、鉴权前置、副作用、错误处理和取消语义不能为缩短等待而被破坏。不要见 await 就全部改成 Promise.all。
- 缓存、组件 memo 和派生状态调整需要具体收益理由。简单表达式或没有重复昂贵工作的地方可以保持原样；不把函数引用变化直接当作已证明的用户可见瓶颈。
- 区分渲染阶段的纯计算、用户事件和与外部系统同步的 Effect；建议优化时保留用户数据、选择状态、交互、错误和加载语义。不得以性能为由掩盖正确性问题。
- 建议验证原交互和相关行为，注明适当观测指标；用户未要求写测试时，不把“必须列固定测试矩阵”塞进每个短答。代码审查不声称已改文件、启动应用或完成 profiler 测量。
- 有充分依据才列问题，没有问题可直接说未发现需要优化的项。用户给“最多 N 项”是上限，不是必须凑满 N 项。

四个用例方向，全部使用原创短代码与合成记录：

1. `independent-versus-dependent-work`：给同一数据加载流程，部分读取独立，另有读取依赖前置结果或权限。请求性能审查并保留调用条件；识别可以重叠的部分，同时不破坏必要依赖与失败语义。接受多种正确安排，不指定唯一 Promise 写法。
2. `avoid-unjustified-memo`：给小型纯展示组件及“交互流畅、没有昂贵重复计算”的明确材料，用户只问是否值得批量加 memo/useMemo。简短说明不必机械改造；不能声称实测缓存收益，也不能把缺证据写成禁止所有缓存。
3. `derived-work-and-state`：给 Effect 中仅根据当前 props/状态计算派生显示值的示例，并提供需要保持的交互与输出条件。识别可避免的更新，提出保持语义的局部做法；不误删真正需要外部同步的行为，不强迫某个具体代码模板。
4. `prioritize-observed-cost`：同页有合成性能记录中的明显昂贵工作和若干轻微可疑模式，用户只要最值得先处理的一项及验证思路。按实际记录选主要问题，保留指标语义，不生成漫长规则清单或凭空宣布优化百分比。

用例注明具体运行假设，不测试未给上下文的框架魔法。评测生成阶段无工具，只验证代码审查答案与建议正确性，不宣称实测应用性能改善。

## B：会议沟通复盘

必要能力：

- 先锁定用户要复盘的行为和目标人，依据给定发言人、原话、轮次或时间定位举例。分清观察、可能影响与建议，不把单次交流扩成稳定人格、动机或领导能力评级。
- “也许、可能、我想”等表达要结合语境，可能是合理不确定性或礼貌。转述、否定和修正也不能当成当事人的原始立场；不能仅按禁词表判回避冲突。
- 发言轮数、字数、句子数和发言时长是不同指标。只有起始时间而无可靠结束信息、存在缺失或重叠时，不用下一个时间戳自动补成时长；不能从文字记录声称听过语音、判断真实语调或识别打断。
- 若用户需要比较会议，保留完整性、时长、参与人数、任务和角色的差异。有充分分母才计算相应比例；可以给窄范围描述，不将缺失样本包装成趋势，也不拒绝所有有依据的比较。
- 给具体、可执行的改进表达，保留说话者本来要表达的事实、责任、条件和尊重。演示改写明确是建议，不回写成真实发言，不编造别人已承诺的截止时间或行动。
- 用户只要一处改进时聚焦一处；仅要会议决议摘录不自动做人际画像或额外行为统计。默认分析提供的材料，不自动扫描、转录、上传、发送反馈或追踪团队成员。

四个用例方向：

1. `turns-are-not-duration`：给发言人明确但只有起始时间、并含转录缺口的短记录，用户询问某人的讲话占比与打断。明确哪些无法计算；可以准确给出已记录轮次，但不能拿轮次替代时长或编造重叠发言。
2. `hedging-in-context`：会议同时有基于证据不足的谨慎表达与一个有文本支持的未回应关键问题片段。用户请求复盘沟通效果；应区分两者并据原话说明，不能因为含“可能”就给人格结论。
3. `compare-with-denominators`：提供两次完整性或参与条件不同的合成摘要及可计算计数，用户询问倾听是否变好。判断实际能比较的指标，指出重要条件差异；任何计算明确分母，不凭总次数直接证明趋势。
4. `one-actionable-rephrase`：给一段有明确事实和角色的会议表达，用户只要一个改进建议和一句示范。输出相应粒度、保留原事实和条件，不发明责任人、日期或承诺；示范不能冒充原始证据。

数量和来源格式若需要严格检查，必须在用户 prompt 中明确；否则允许清楚可定位的等价引用。统计口径放入材料或合理分析标准，不要求未提供的数据。

## 生成前预检：由主任务检查用例

这一步是两个执行任务之间的质量检查，不向用户索取新授权。

1. 实施者先写上述八例的实际 prompt、合成材料、must_include 和 must_avoid，以及简短评分说明。每条必要标准注明来自哪一用户要求、输入事实或任务不变量，记录可接受的等价回答。
2. 自查最多/恰好、或/且、未知/否定、来源定位/固定 ID、建议/已执行等边界；不得在评分阶段临时变严，也不能为迎合 baseline 临时放宽。
3. 在首次模型生成之前把用例路径和评分摘要回传主任务做只读预检。此时可以继续必要来源核查和运行器检查，但不要运行八例 baseline，也不要先写技能正文。主任务无需用户介入即可给出修改意见或确认。
4. 预检意见处理后冻结用例及评分，再按下面顺序运行。不要发起相互 wait_threads 的等待循环；实施者回传后结束该阶段，主任务读到结果后会继续派发。

评分说明可保存在 docs/fifth-absorption-report.md 的“运行前评分设计”部分，随阶段更新状态；不要另建一套通用评测平台。

## 实施顺序和运行上限

1. 第四批提交、来源阅读、八例编写与主任务预检完成后，冻结全部输入和评分规则。
2. 运行八次无技能 baseline，再编写并冻结两包。隔离生成会话只能读公共指令和该例材料，不能读设计方案、评分、上游全文、既有答案或其他技能。
3. 包按本仓库两字段 frontmatter 编写，内容精简；示例与引用仅在确有价值时添加且须包内自包含。不要只换用例名称或数字就复刻成演示。
4. 登记两包，记录包指纹；如用例 stage 从 planned 改为 active，只改变该字段并保留前后快照。用相同请求和公共指令运行八次 skill 组，有意差异仅为所属完整包。
5. 共十六次有效单轮生成，`gpt-5.6-sol / medium`，沿用此前已授权的纯合成 CLI 路径。全轮启动器失败最多修正补跑一次，保留所有尝试；不修改失败用例或反复重跑选择好看结果。真实审批工具的拒绝如实报告，不绕过。
6. 逐项记录满足、未满足或证据不足及对应输出片段，再汇总全约束成绩和核心任务成绩。存在未满足的必要项就不能全约束通过。模型评分与主任务模型复核均不是独立人工评审。
