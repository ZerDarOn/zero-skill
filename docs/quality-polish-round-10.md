# 第十轮质量打磨：React 原生盲测与虚拟焦点

日期：2026-09-11。

## 结论

`react-performance-review` 从 0.1.1 升至 0.1.3，当前完整包 SHA-256 为 `66411b82b4075b8ad839cb75fce155ead7beff2170816591a6dab642116e05c6`。本轮没有增加活动用例，技能仍为 `experimental`，`evidence` 仍为 `null`。

第一次六题、三次重复的原生盲测没有证明 0.1.1 优于无 Skill。冻结严格分反而是无 Skill `66/72、15/18`，0.1.1 `64/72、13/18`。揭盲后发现两个评分要求比用户可见任务更窄：R02 强制写出可控时钟，R06 强制写出 DOM 焦点交接与焦点验证。保留原分后按用户可见核心任务另做诊断性语义重算，两组均为 `72/72、18/18`。这项重算不替代正式盲分。

真正有用的发现是：两组在 R06 三次都只写了选中、滚动和集合语义，没有说明虚拟目标挂载后的实际焦点交接，也没有验证真实焦点或有效活动项关系。这个共同失败触发了后续小步修订。

## 未见题与冻结方法

六个合成题在 0.1.1 编写后建立，覆盖：

- Context `value` 身份与已测消费者重渲染；
- 为减少 interval 重建而引入 stale closure；
- 受控输入与 Transition 的紧急／非紧急更新边界；
- debounce 后仍存在的迟到响应竞态；
- `useSyncExternalStore` 快照身份；
- 10,000 行虚拟化中的稳定身份、键盘导航和集合语义。

运行前，另一个同项目任务在不读取 Skill 正文和历史结果的情况下复核题面。它修正了 Context 普通父子渲染混杂、一个隐藏验证要求、一个与旧用例重复的廉价缓存题，以及 primitive 快照消费形状、未挂载 `aria-activedescendant` 两项机制错误。修正后才冻结。

每个正式 Skill 臂都显式调用冻结包；无 Skill 臂不安装技能。模型为 `gpt-5.6-sol`、medium；临时 Git 根、用户目录和 `CODEX_HOME` 相互隔离，断网并关闭 apps、plugins、MCP、网页搜索和多代理。另一个任务只读取匿名 packet 与评分表，保存逐项布尔判断后才由计分器揭盲。

## 第一次六题结果：0.1.1 对无 Skill

| 实验臂 | 冻结标准通过 | 完整输出 | 盲评偏好 | Token | 估算成本 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 无 Skill | 66/72 | 15/18 | 2 | 176,659 | 0.2779256 |
| 0.1.1 | 64/72 | 13/18 | 0 | 205,806 | 0.4634832 |

R01、R03、R04、R05 两组均三次完整通过。R02 的两个 0.1.1 回答完整覆盖当前值、切换房间和卸载，只是没有明确说“假计时器或可控时钟”；这不应被宣传成核心正确性退化。R06 两组各三次都漏了窄焦点要求，是稳定的审查完整性缺口。

按用户可见任务重算时，R02 接受不指定时钟实现但覆盖正确行为的验证；R06 接受跨窗口选中、滚入可见、稳定身份和读屏集合语义，而不追加题面未明说的 DOM 焦点细节。两组因此均为 `72/72、18/18`。冻结标准、原评分和候选输出均未改写。

## 0.1.2：补齐虚拟化与可控调度

0.1.2 增加两条窄规则：

1. 窗口化、虚拟化或 DOM 复用必须保留稳定数据身份、选择、跨窗口键盘导航、挂载后焦点交接、滚动定位和完整集合语义。
2. 计时、取消或响应顺序影响结论时，优先用可控时钟、可控 Promise 或等价调度稳定复现。

旧版 0.1.1 原字节快照包指纹为 `8ce9d88b07c40e62405b978ed1c21f272f27c14b8c6d311531ac7b23bf5369d0`，0.1.2 包为 `aa85658bfa3905fed60127013b7a21150aeeef175539e09097d06bd798ee3496`。

先把“不可真实等待”和“焦点必须跟随选中项”直接写入任务。两题各三次的结果如下：

| 实验臂 | 标准通过 | 完整输出 |
| --- | ---: | ---: |
| 无 Skill | 24/24 | 6/6 |
| 0.1.1 | 24/24 | 6/6 |
| 0.1.2 | 24/24 | 6/6 |

这个天花板结果说明用户把边界说清楚时，基础模型和旧版都能完成任务，不能证明 0.1.2 带来版本收益。

随后用第一次 R02/R06 的原始自然提示和原始冻结标准重跑：

| 实验臂 | 标准通过 | 完整输出 | 盲评偏好 |
| --- | ---: | ---: | ---: |
| 无 Skill | 17/24 | 2/6 | 0 |
| 0.1.1 | 18/24 | 2/6 | 0 |
| 0.1.2 | 22/24 | 4/6 | 2 |

0.1.2 在 R02 三次都提出可控计时验证；0.1.1 与无 Skill 各为两次。R06 中 0.1.2 三次都给出挂载后焦点交接方向，但两次没有把实际焦点写进验证，因此仍少 2 分。

## 0.1.3：把焦点验证写完整

0.1.3 只补一句：任务涉及焦点时，方案要说明目标进入窗口后的交接，验证要检查实际焦点或有效活动项关系；只检查选中和滚动不够。

在完全相同的原始 R06 上，无 Skill、0.1.1、0.1.2 与 0.1.3 各重复三次：

| 实验臂 | 标准通过 | 完整输出 | 盲评偏好 |
| --- | ---: | ---: | ---: |
| 无 Skill | 8/12 | 0/3 | 0 |
| 0.1.1 | 7/12 | 0/3 | 0 |
| 0.1.2 | 9/12 | 0/3 | 0 |
| 0.1.3 | 12/12 | 3/3 | 3 |

0.1.3 三次都同时说明了挂载后焦点交接和实际焦点／有效活动项验证。这个结果支持修复本次窄失败，不支持一般 React 性能排名。

最后用当前 0.1.3 对六题各做一次广覆盖回归：无 Skill `22/24、4/6`，0.1.3 `23/24、5/6`。R01、R02、R03、R05 两组完整通过；R06 只有当前包完整通过。R04 两组都提出正确的取消或代次门禁，但没有显式复述“清 timer 不能阻止已发出的旧响应”，按冻结标准各少 1 分。单次结果只用于查明显退化，没有证明稳定总分优势。

## 上游和官方机制

机制边界参考 React 官方 `useTransition`、`useSyncExternalStore` 和 `useEffectEvent` 文档。当前官方参考页显示 19.3；本轮合成任务沿用仓库既有的 React 19.2 条件，因此只采用这些 API 的相关机制，不把当前版本页当作 19.2 的完整兼容性证明。

Vercel `react-best-practices` 固定入口提交为 `063bee94c3f4df8453406c830b0a7df0f2860278`，入口 frontmatter 声明 MIT，任务匹配度较高。但本轮未能把入口引用的完整规则闭包和独立许可证正文固定到本地。残缺副本会让第三臂先天吃亏，因此没有强行加入。高星和规则数量只作为发现线索。

## 证据边界

本轮共发起 98 次真实 Codex 生成：2 次 R01 基础设施预检不计分，96 次进入五组正式比较。正式比较含 39 个匿名 review item。所有 provider 行完整，未出现外部工具轨迹。

这些结果仍有明确限制：

- 评审是另一个同项目模型任务，不是独立人工或无障碍专家；
- 只评静态审查回答，没有运行 React 应用、浏览器 Performance、Profiler、键盘 E2E 或读屏器；
- 所有 Skill 都显式调用，不能证明隐式发现；
- 0.1.2、0.1.3 的定向题来自已观察失败，只能证明修复这些条件；
- 当前六题广覆盖只有一次重复，不能据此宣称稳定胜率；
- 没有任务匹配且材料闭包完整的第三方 Skill 实验臂。

因此保留 `experimental`。下一步应在可运行的最小 React fixture 上验证焦点、取消竞态和提交次数，再决定是否将这些结果升级成真实运行时证据。
